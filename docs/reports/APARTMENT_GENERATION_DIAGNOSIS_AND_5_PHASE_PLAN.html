Part 2 — The problems

P1 — Schematic hard-fails for any flat count other than 2, 3, or 4 CRITICAL

Evidence: schematic.ts branches length===2 / ===3 / else; the else always builds exactly 4 quadrant units. flatCount = finalFlats.length, but units pushed = 4. Then validateSchematicMatchesManifest checks schematic.units.length === manifest.units.exactCount.

  • 1 flat → schematic builds 4 → mismatch → schematic_validation error → no image at all.
  • 5, 6, … → builds only 4 → mismatch → hard stop.
  • Only 2/3/4 ever reach FLUX.

Effect: Directly blocks your "1, 2, 3, 4, 6, any … villas too" requirement.

P2 — A ~120-line prose prompt sent to a distilled 4-step model CRITICAL

Evidence: compileApartmentFloorPlanImagePrompt() assembles priority rules, per-unit breakdowns, "HARD REQUIREMENTS 1–11", organisation sentences, forbidden-text lists. flux-2-klein-4b is a distilled model with fixed 4-step inference (Cloudflare confirms steps can't be changed). Few-step models follow long instructions and render exact counts/text poorly.

Effect: Overlapping rooms, wrong flat/lift/stair counts, villa-like/gibberish output — exactly what memory §55 warned about.

P3 — Square 1024×1024 output, no aspect adaptation HIGH

Evidence: both compilers default width/height = 1024; plot aspect ratio is never mapped to image size. Effect: Real plates (and your references) are rectangular/portrait; a square canvas cramps multi-flat layouts → overlap. klein supports non-square output up to ~4 MP.

P4 — Zero-tolerance preflight is what stamps "score 0" HIGH

Evidence: evaluateApartmentPreflight fails on any deviation; the orchestrator then pushes the candidate with overallScore: 0, status: REJECTED, evaluation: null — interpretation/validation/real scoring never run. Effect: Because P1–P3 make output structurally wrong, nearly everything is rejected and shows as 0. That "0" is a gate placeholder, not an architectural score. Gemini also miscounts on garbled images, compounding rejects.

P5 — Gemini model IDs are fragile / likely invalid → all Gemini stages can 404 HIGH

Evidence: .env has GEMINI_MODEL=gemini-flash-lite-latest, fallback gemini-3.1-flash-lite; env.ts default gemini-3.6-flash. In gemini.ts, 400/404 throws immediately. gemini-3.1-flash-lite/gemini-3.6-flash are not real Google IDs. Effect: If the primary alias is unavailable, understanding + preflight + interpretation + evaluation all fail — independent of image quality.

P6 — References are weak and can be silently dropped HIGH

Evidence: the schematic PNG (schematic-renderer.ts) is a crude colored-rectangle diagram; rooms are placed on a naive 3×3 grid regardless of adjacency. On a 400 with references present, the provider silently retries without any references (only a console.warn). Effect: The style-enforcement mechanism is both low-value and unreliable; a 4-flat reference also fights a 2-flat request.

P7 — Unsupported request fields may cause the UI "fetch failed" MED-HIGH

Evidence: buildCloudflareImageRequestBody() adds steps and (by default) negative_prompt. klein's documented multipart params are prompt/width/height (+ images); steps is fixed and negative_prompt isn't documented. The 400-fallback only fires when references are present and never strips these fields. Effect: A 400 on unknown fields (or a timeout on 4 large images) surfaces as generic fetch failed. Transport design is fine; the payload is over-specified.

P8 — Image handed to Gemini via a brittle regex MEDIUM

Evidence: preflight/interpretation/evaluation embed the image as text IMAGE (base64 mime):\n…; buildGeminiParts() regex converts it to inlineData. Any wording change silently sends a multi-MB base64 string as text → vision fails. Effect: Latent failure on the next refactor.

P9 — Villa / bungalow path is under-served MEDIUM

Evidence: residential_independent uses compileFloorPlanImagePrompt() — reasonable, but still square 1024, no references, weaker label guards. Effect: "Adapt for villas/bungalows" is only partially met.

P10 — Consistency / typing niggles LOW

  • Default setbacks differ: manifest.ts {3,2,2,2} m vs schematic.ts {4.5,3,3,3} m.
  • Two DeterministicApartmentSchematic definitions (renderer imports from types/apartment); confirm identical shape.
  • image-quality-gate.ts uses byte-variance as a detail proxy — coarse, not structural.

Part 3 — Reference images

What you uploaded is the right visual language: top-down orthographic, black-on-white technical linework, central lift/stair core, dry balconies, sit-outs, ducts/OTS, English labels. Images #1–#3 are 4-flat, mostly portrait plates.

The catch: all show 4 flats. A 4-flat reference pulls a weak model toward 4 even when the user asks for 2. Memory §27: user count wins. So references must be selected to match the requested count, not thrown in blindly.

Part 4 — Solution direction (the decision that shapes everything)

Memory §60 already gives the escape hatch. Two architectures:

Option A — Reference/schematic-guided FLUX (current intent). Short structured instruction + strong schematic image + count-matched references. Ceiling: nicer plates, but exact counts stay probabilistic on a distilled model, so the strict gate still rejects a share.

Option B — Deterministic base-plan → FLUX as styling layer (§60 fallback). The engine already produces exact geometry; render it to a clean base plan, use FLUX only to stylise (or skip FLUX for the authoritative 2D). Reliable when counts are non-negotiable — which is your requirement.

Recommendation: Pursue A for visual quality but make B the guarantee of correctness. The deterministic schematic is the source of truth for counts/zoning; FLUX renders that layout (image-to-image / strong reference) rather than inventing one from text. If FLUX misses after a bounded retry, fall back to the deterministic base-plan render so the user still gets a correct, editable plan. This satisfies "exactly N flats for any N" and villa adaptation without betting correctness on a 4-step model.

Part 5 — The five phases

Each phase is shippable and ends with an acceptance gate. Order follows memory §67.

Phase 1 — Unblock arbitrary flat counts + fix transport & model config

Goal: Make any configuration (incl. 1/5/6 flats and villas) reach FLUX and return a byte-valid image; stop generating on invalid model IDs / rejected payloads. Addresses: P1, P5, P7, P10.

  1. Generalise schematic.ts to partition the plate for N flats (drop hard-coded 2/3/4/else); ensure schematic.units.length === flatsPerFloor === manifest.units.exactCount for all N. Add single-unit and villa paths.
  2. Pin real Gemini model IDs in .env/env.ts; verify with a smoke call; remove fictional fallbacks.
  3. Trim FLUX payload to documented klein params (prompt/width/height + images); drop steps/negative_prompt or gate them; add a transport log so "fetch failed" is diagnosable.
  4. Reconcile setback defaults; unify the schematic type.

Gate: flat counts {1,2,3,4,6} and villa reach the FLUX call (no schematic stop) and return a byte-valid PNG; a no-reference/no-negative klein request returns 200+PNG; a one-shot Gemini call returns text.

Phase 2 — Replace prose with a compact instruction + count-matched references

Goal: Stop asking a distilled model to read an essay; let the schematic image carry structure. Addresses: P2, P3, P6, P9.

  1. Rewrite compileApartmentFloorPlanImagePrompt to a short directive; keep the manifest as metadata/logging, not prose.
  2. Derive width/height from plot aspect (portrait/landscape), within klein limits; never force square.
  3. Upgrade the schematic scaffold into a readable line drawing (labelled rooms, core, [X][X] lifts, hatched stairs) worth sending as input_image.
  4. Select references from the flats_N/villa bucket that matches the request.
  5. Record silent reference drops on candidate diagnostics.
  6. Apply the same aspect + reference logic to the villa compiler.

Gate: On the §65 scenario (2 flats: 1×2BHK+1×3BHK, 2 lifts, 2 stairs, lobby), at least one seed yields an image a human agrees looks like a 2-flat Indian plate (manual acceptance — 200 ≠ success); output aspect matches the plot.

Phase 3 — Make the gate honest + add the deterministic fallback

Goal: Distinguish "gate-rejected" from "scored"; guarantee a correct editable plan even when FLUX misses. Addresses: P4 + the correctness guarantee.

  1. UI/state: a preflight rejection reads "Rejected at visual preflight: reasons", not "Score 0/100". Reserve 0–100 for real evaluation.
  2. Bounded seeded retry (memory §20); if still failing, fall back to rendering the deterministic schematic as the authoritative base plan, marked FALLBACK_DETERMINISTIC (never claim FLUX succeeded — §45).
  3. Let preflight advise rather than hard-block once the fallback enforces exact counts — without weakening count guarantees.

Gate: The §65 scenario always yields exactly the requested flats/lifts/stairs (FLUX pass or deterministic fallback); no gate-rejected image ever shows "0" as an architectural score.

Phase 4 — Strengthen image→2D interpretation & hard validation

Goal: Turn the accepted image (or base plan) into a validated canonical 2D model reliably. Addresses: P8 + apartment validation depth (§41–§43).

  1. Pass images to Gemini as real image parts (explicit field on complete()); retire the regex dependency.
  2. Apartment-aware interpretation: capture per-flat grouping, core, lifts, stairs, lobby; normalise into canonical geometry.
  3. Apartment-specific hard validation: verify unit count, party-wall separation, core presence, and manifest-match before acceptance. Deterministic validation stays authoritative (§42).

Gate: An accepted plan interprets into geometry that passes hard validation, with validated counts equal to the manifest; interpretation no longer depends on prompt wording.

Phase 5 — Gemini evaluation, honest stage UX, and the scale sweep

Goal: Advisory 0–100 on valid plans; unmistakable stage UI; prove scaling across counts and building types. Addresses: P9 completion, §48–§49, §66.

  1. Run evaluatePlanArchitecturally only after hard validation; show categories as advisory (§43).
  2. Honest stage UI (§49): true current stage with real per-stage state; never fake progress or show a failed stage as success.
  3. Scale sweep as acceptance: run the full loop for 1/2/3/4/6 flats and a villa, confirming exact counts and adaptation.

Gate: The §66 end-to-end loop works for §65 and the scale sweep; quality-gate discipline recorded (focused/package tests, typecheck, lint, real smoke test) using INTERNAL ENGINEERING GATE PASSED / PROFESSIONAL REVIEW REQUIRED language, never "should pass."
